# Alius

SillyTavern extension (TypeScript). Design docs live in `docs/`.

## Before any work
0. Sync the working branch with GitHub first. Cloud sessions can start on a stale local `unstable` (an old commit left in the container, shown as "up to date"), so run:
   `git fetch origin unstable && git checkout -B unstable origin/unstable`
   (the clone is shallow, so a fetch may report a "forced update" that is not one; the remote history is intact). Then check that the branch contains every implemented package (`docs/00-overview.md` §9 has the status table); a stale clone once lacked P1. Run `npm test` to know the baseline.
1. Read `docs/00-overview.md` (always; §5.4 lists the engine interfaces that already exist).
2. Read the plan you are told to execute (in `docs/plans/`) and the spec it names. If the task names a package spec and no plan exists, write the plan first (same format as the existing ones). Specs of implemented packages end with **Implemented as**: where it differs from the draft, the code wins.
3. Read `docs/content/lore.md` every session (world, tone, and §0: the squad is women, the player is of any gender, so no pronoun for the commander in any text a player or the main model reads). Read the other files in `docs/content/` only if the task says so.

## Rules
- **Memory check (every package that adds a mechanic).** When you write a plan or a package that introduces an engine event, a decision, a consequence or a piece of state the squad could remember, decide it explicitly and write the verdict in the plan (a task or a Global Constraints line): either a `memoryRules` entry plus a resolver for each event worth remembering (who knows it: `audience`; who hears of it later: `spread`; how much it matters: `importance`; `hiddenFromCommander` if the commander must not know), or one line saying why nothing is remembered (the site already writes a fact, it is a squad secret, it is pure bookkeeping). Also say whether the new text reaches the journal (`eventDeltas[].journal` for a new relation event), the chronicle (an `audience` on every new chronicle line) or a prompt (a `group: 'memory'` provider). A package that skips this is not finished; the reviewer checks it. Details and the rules for each: `docs/packages/P3b-memory.md` (**Implemented as**).
- Follow the plan task by task; do not skip the failing-test step.
- After each finished task: tick its checkboxes in the plan file, commit.
- Never put `dist/` or `style.css` into .gitignore — they are committed on purpose.
- Stop at the task boundary you were given; don't start the next chunk.
- If the plan and the code disagree, stop and report instead of improvising.

## Releasing a version
A *version* (0.1.0, 0.2.0, …) is a whole release, not a package. When the user says a version is ready (and only then):
1. Bump the version in `package.json`, the root of `package-lock.json`, `manifest.json` and `content/core/manifest.json`.
2. Add its section on top of `CHANGELOG.md` (`## X.Y.Z — YYYY-MM-DD`), written for players who do not know the code, in the same style as 0.1.0: grouped by area, every main change, known limitations last. Update `README.md` / `docs/README.md` if they name the version.
3. Run `npm test` and `npm run typecheck`, commit, push the branch.
4. Tag the release commit with an annotated tag `vX.Y.Z` (`git tag -a vX.Y.Z <commit> -m "Alius X.Y.Z — see CHANGELOG.md"`) and push it (`git push origin vX.Y.Z`). Cloud sessions may be refused a tag push (HTTP 403: they push only their branch); then do not work around it, give the user the exact commands to create and push the tag themselves.
