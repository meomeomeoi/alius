# P5 — World Map, Expeditions, Missions & Director

**Depends on:** P0–P4. **Read:** overview; `content/lore.md` (§3, §4, §6, §7).

> **Historical spec.** This package is implemented; where this text and the code differ, the code is the source of truth (see **Implemented as**).

**Status:** implemented (plan: `plans/2026-11-09-p5-world-expeditions-director.md`). Automated tests pass; the in-SillyTavern checklist `MANUAL_TEST_P5.md` still has to be run by hand. Where an earlier draft of this spec said something else, the code won; the differences are listed under **Implemented as** at the end.

## Goal

The world moves: a world map with regions, a mission board fed by command and by the story, rumors in the PDA, expeditions as node-map runs, and a director that steers authored spine beats, threads and clocks from world state and the player's decisions.

## 1. World state

- `clocks[]`: `{ id, label, segments, filled, regionId?, onFill: effectIds, visibleToPlayer }` (e.g. Bloom spread in a region, rival corp operation, oversight suspicion).
- `threads[]`: `{ id, title, status: 'open'|'resolved'|'failed'|'dormant', flags[], relatedUnits[], relatedRegions[], createdDay }`.
- `factions`: standing −100…100 per corporation/faction.
- `flags[]`: consequence flags from decisions (`delivered_evidence_vesper`, `spared_survivors_k12`…).
- `spineProgress`: current beat index + beat states for the chosen start.
- `clearanceTier`: raises level caps (P4); granted by spine beats and certain missions.

## 2. World map (MAP tab)

- Author-supplied image (`content/core/map/world.png`) with region hotspots (polygons in `regions`). Fallback: ASCII region map.
- Region panel: environment, danger, known enemy categories, active clocks, available missions, points of interest.
- Selecting a mission/POI opens the expedition planner.

## 3. Missions (OPS tab)

- Mission: `{ id, source: 'command'|'story'|'rumor'|'side', title, brief, regionId, danger, objective (node type + condition), deadlineDay?, rewards {credits, plyx, items, clearance?, faction}, failureEffects, threadId?, spineBeat? }`.
- Deadlines are generous (default ≥ 5 days); command missions failing affect oversight/faction standing and Leash authorizations (P6).
- Rumors: short BBS-style posts (`RUMOR MILL` board look) that can convert to side missions or facts; generated by the director, more with Comms level and Insight.
- Board size limited by Comms level.

## 4. Expeditions

- Planner: choose up to 4 units (+ formation rows), loadout check, supplies to bring (rest nodes consume), duration estimate (2 or 3 slots).
- **Node map** generated from region template + mission: 3–5 layers, 2–3 nodes per layer, branching edges; node types (`nodeTypes` registry): `combat, elite, event, cache, rest, unknown, objective, crisis` (crisis = Commander Crisis combat). Fog: only adjacent nodes revealed (Echo Bleed / scouting reveal more).
- ASCII rendering: `[⚔]──[?]──[≡]` style with path highlight.
- Event nodes: from `dilemmaTemplates` with `scale: 'minor'` (P6 provides the full dilemma system; P5 ships simple fixed-option events with costs) or flavor-only.
- Between nodes: swap rows, use consumables, check stress.
- Retreat any time (lose unbanked loot).
- Return: resources banked, `expedition_recap` (main model, optional by setting) generated from the structured combat/event log, shown as an "AFTER-ACTION REPORT"; then P3 receives expedition intents (`protected`, `endangered`, `sided_with/against` from event choices) and the debrief hook (optional scene with any unit).

## 5. Director (`director_tick`, mechanic profile)

Runs at day end (P2 pipeline) and after expeditions. Engine assembles a compact world digest: day, spine beat + its goal, open threads, clocks, faction standings, recent major flags, squad relationship highlights (states only), mission board.

Output schema:
```
{
  missionOffers: [{ templateId, regionId, danger, title, brief, objectiveNode, deadlineDays, rewardsTier, threadId?, spineBeat? }] (≤2),
  rumors: [{ text (≤40 words), leadsTo?: 'mission'|'fact'|'none', tags[] }] (≤3),
  threadUpdates: [{ threadId|'new', title?, status?, addFlags?[] }],
  clockAdvances: [{ clockId, by: 1|2, reason }],
  storyBeatProposal?: { beatId, framing (≤60 words) }
}
```
Engine validation: ids exist, rewards come from tier tables (the model never sets amounts), max clock advance per tick, spine beats only when beat conditions are satisfied, at most one story-beat proposal per 3 days (setting). Rejected parts are dropped silently (debug log).

**Spine:** each start has 5–8 authored beats with `conditions` (flags, days, clearance, thread states) and `goal`. The director chooses *when* and *how* to frame them (mission, rumor, incoming unit, event), never skips or invents spine beats. After the last beat, the director runs open-ended from clocks/threads/factions.

**Incoming named units:** a story/mission outcome can offer "new unit available"; the player imports a card via the short P1 wizard (or declines; a grunt joins instead).

## 6. Context contribution

Provider adds 1–3 sentences of world state relevant to the scene (region of last expedition, active thread involving present units, clocks above 50%).

## Acceptance criteria
1. Map shows regions (image or ASCII), missions per region, clocks.
2. Missions from command, story, rumor and side sources appear; deadlines tick; failure effects apply.
3. An expedition from planner to return works with combat, event, cache, rest and objective nodes; retreat works; loot banked.
4. After-action report generated from the structured log; P3 intents from the expedition applied.
5. Director output with invalid ids/amounts never mutates state; spine beats only fire when conditions hold; open-ended phase continues after the spine.
6. Clearance tier raises the level cap.
7. Tests: node map generation (seeded), digest builder, director validation, clocks, deadlines.

## Interfaces already provided by P2 (implemented — use, do not rebuild)

- **Expedition slots:** `calendar/consume_slot { slots: 2 | 3, reason: 'expedition' }`. It is only accepted while that many slots are left today (Morning: 1–3, Afternoon: 1–2, Evening: 1), so a 2-slot expedition starts in the Morning or Afternoon and a 3-slot one only in the Morning, and not while a talk is open. Spending the Evening runs the day-end pipeline once.
- **Day-end pipeline:** `registerDayEndStep('mission_deadlines', fn)` and `registerDayEndStep('director_tick', fn)` (and `dm_rumors` for rumor generation). Hooks receive `(draft, { registries, rng })`, may mutate `draft` and return events; a throwing hook is isolated (changes dropped, `day_end_step_failed` emitted) and the day still ends.
- **Rumors / side jobs:** the `scout_net` activity emits `rumors_requested` and adds Insight points; the number of rumors per day is `facilityEffect(state, reg, 'comms', 'rumorsPerDay')`, the mission board size `'missionBoardSize'`.
- **Supplies:** P2 only drains them (every living unit + commander per day, `hunger_loop` ×2, mess hall reduces it) and offers `base/requisition` (credits → supplies, 3 CR each) as a stopgap. Expedition loot and rest-node supplies are P5's; consider removing the stopgap or retuning its price.
- **Credits/plyx:** `state.resources`; mission rewards should change them through an action in P5 (never directly from UI).
- **Incoming named units:** the P1 wizard model (`src/setup/wizard.ts`) is reusable; capacity is `roster.capacity` (barracks), grunts count against it.
- **Grunts as rewards/replacements:** `generateGrunt(state, reg, rng)` is pure.
- **Region/start:** `state.world.startId` and the start's `startingRegionId` (via the corporation) are set by P1.

## Interfaces already provided by P3 (implemented — use, do not rebuild)

- **Debrief and event scenes:** start them with `app.startScene({ locationId, participants, origin: 'debrief' | 'event', consumesSlot? })`, which dispatches `scene/start`, activates only the participants in the group chat, sets the scene context and shows the scene screen (`app.scene` has `send`, `propose`, `end`, `resume`). `consumesSlot: false` makes the scene free. Up to three named, living participants; locations come from the `locations` registry (add ids there).
- **Memory:** `addFact(draft, { about, text, tags, importance, day, knownBy })` (from `engine/memory`; `knownBy` is a list of unit ids or `'*'`; the commander always knows) and `recordPromise`. Facts tagged `crime` reveal the commander's crime to the unit(s) that know them; facts tagged `affair` can force the discovery of a secret affair.
- **Night entries:** `enqueueNight(draft, entry)` (`NightEntry = { id, unitId, kind, priority, framing, ignore: { event, severity }, expiresDay }`; one per unit+kind; highest priority first; entries expire; `framing` is shown as the knock). P2 moves the head to `calendar.nightEvent` at the end of Evening.
- **Intents after an expedition:** feed `protected` / `endangered` / `sided_with` events through `intents/apply` inside a debrief scene; the engine validates and applies them (diminishing returns included).
- **Chronicle:** scene lines are written by `scene/end`; the weekly/daily compaction runs by itself (`memory/compact`); add story beats as facts or as chronicle entries via `addChronicle(draft, { kind: 'scene', day, text })` if needed.
- **Director context:** `ContextBuilder` providers registered by P5 sit next to P3's (`scene_header` 95, `units` 90, `commander` 80, `facts` 70, `promises` 60). The relationship `promptHint`s are in `relationshipStates.json`.

## Interfaces already provided by P4 (implemented — use, do not rebuild)

- **Starting a fight:** `app.startCombat({ encounter, formation, coverId?, bankLoot?, expedition: true })` (shows the combat screen; `allowRetry` comes from the easy-retry setting). Build the encounter with `generateEncounter(state, reg, rng, { table: region.enemyTable, danger, squadPower, exposesCommander?, lootTableId? })` and the formation with `defaultFormation(state, reg, unitIds)`; `checkStart` says why a payload is refused; `canAutoResolve` offers AUTO. All are exported from `engine/combat`.
- **Result:** a decided combat leaves `state.lastCombat` (`outcome`, `rounds`, `enemies` with names, `xp`, `levelUps`, `loot`, `injuries`, `deaths`, `breakdowns`, `stressDelta`, `relationHints`, `commanderInjured`) and no `combat`. With `bankLoot: false` the loot is only recorded: bank it on return with `bankLoot(draft, lastCombat.loot)` (a lost or retreated combat has none). Chosen cache nodes use the loot table `loot_cache`.
- **Debrief:** pass `lastCombat.relationHints` to `intents/apply` inside the debrief scene (`protected` / `endangered` with actor, targets and severity).
- **Breakdowns** last until the expedition ends: call `squad/release_breakdowns` on return (emits `breakdown_released { unitId }`; queue the debrief/night hook from it).
- **Level cap:** write `world.clearanceTier` (0–3 → caps 10/20/30/40) when a beat or facility raises it; stored XP is spent by the next `applyLevelUps` (the next activity or combat).
- **Injuries** use P2's `status: 'injured'` + `injuryDays`; a downed named unit is never dead, grunts die on a loss.
- **Rows between nodes:** `squad` formation is chosen per combat; the engine accepts any valid formation each time.

## Implemented as

### Architecture
- **Pure rules under `src/engine/world/`** (one file per concern: `types`, `state`, `effects`, `clocks`, `missions`, `spine`, `nodeMap`, `expedition`, `director`, `index`); actions in `src/engine/actions/world.ts` and `expedition.ts`. The non-engine layer is `src/world/` (director and expedition controllers, the `world` context provider); like `src/scene` it reaches ST only through `import type` and never imports the UI (architecture tests).
- **One consequence vocabulary.** Every consequence outside combat is a **world effect** (`resource`, `carried_supplies`, `faction`, `clock`, `flag`, `clearance`, `party_stress`, `party_hp`, `loot`, `leash`, `thread`, `unit_event`, `incoming_unit`, `fact`, `offer_mission`; see `CONTENT.md`) run by `applyWorldEffects`; nested chains (a clock's `onFill`) stop at depth 3.
- **The director is two-phase.** The day-end pipeline is synchronous, so the engine opens `world.director.pending = { id, reason: 'day_end'|'expedition'|'scout', day }` and emits `director_requested`; `src/world/directorController.ts` makes the `director_tick` call and answers with `director/apply { requestId, output, beatCooldownDays? }`, or `director/fallback { requestId }` when the call fails, the setting `directorEnabled` is off or no profile exists. A wrong or repeated id is refused (`Stale director answer.`); a request still open at the next day end is answered by the engine's own fallback first. `rumors_requested` (P2 `scout_net`) becomes `director/request { reason: 'scout' }`, of which only rumors are applied. One validator (`validateDirectorOutput`) serves both answers.
- **An open expedition confines the campaign:** only `expedition/*`, `combat/*`, `director/*`, `debug/*` and `relations/commander_injured` (the night-visit roll after a Commander Crisis, which only happens inside a run) actions run (`expedition_open` error otherwise). Slots are spent **once, on return** (`consumeSlots`, so the day may end inside the return); `expedition/start` only checks that enough are left.

### Rules
- **Fallback director** (`fallbackOutput`, seeded, registry ids and authored texts only): a command mission every `commandEveryDays = 3` days while none is open, one side mission when the board has room (core: `tpl_hunt`), one authored rumor line of a known region, +1 on one region clock on even days, the current spine beat as soon as it may start. Thirty days of fallback-only play reach the open-ended phase when story missions are completed on offer.
- **Director source rule:** the first command-capable offer of a tick becomes the (single) open `command` mission; every other offer is a `side` mission limited by the board size, or is rejected when the template allows no side mission. Threads: reopening a closed thread counts against the 6-open limit; the newest 20 closed and 6 dormant non-spine threads are kept.
- **Content removed under a save:** a vanished story mission frees its beat (`spine.proposed` cleared); an event whose template is gone, or a fight that cannot be built, resolves as `Nothing here.` and finishes an objective node; a `win` objective must use a combat-kind node (checked at load). A retreat after a fight that is decided but not yet taken into the run first takes it in.
- **Validation limits:** ≤ 2 offers, ≤ 3 rumors (and at most the day's room), ≤ 40 words per rumor, ≤ 60 per framing, clock `by` exactly 1 or 2, ≤ 2 per clock and ≤ 3 in all, one new thread per tick (≤ 6 open non-spine threads, ≤ 12 dynamic flags per thread, `thread:<id>:<slug>`), `spine:*` threads untouchable, amounts never read from the model. The digest (`buildDigest`) has no relationship numbers or unit ids and shows the newest 4 flags per thread.
- **Missions.** Offered missions are the board (size = comms `missionBoardSize`); `side`/`rumor` offers are refused on a full board, `command`/`story` offers push out the oldest `side`/`rumor`. An expedition makes its mission `active`; success pays (`rollRewards`: credits/plyx inside the tier ranges, tier loot, faction from `template.factionId` + tier, clearance from the template) and runs `onSuccess`; a retreat or lost fight puts it back on the board; `failureEffects` apply only when the deadline passes (`mission_deadlines` day-end step; content that vanished expires without effects). Story missions have no deadline.
- **Points of interest** are standing scavenging runs: `expedition/start { poi }` creates an `active` `side` mission from the POI's template (never on the board), with a cooldown of 2 days per POI.
- **Spine.** `world.spineProgress` counts completed beats; `world.spine = { proposed?, proposedDay?, lastProposalDay? }`. Proposing the current beat (conditions `minDay`, `flagsAll`, `flagsNone`, `clearanceMin`, `threads`) stores the framing as a public fact and chronicle line, opens thread `spine:<id>` and, for `mission` completion, offers the story mission; the beat completes when that mission succeeds, one of `anyOf` flags is set, or at once (`auto`), then runs `onComplete`. Until P6 the "choice" beat 4 completes through a pinned fixed-option event that sets one of three declared flags.
- **Node map.** 3–5 layers of 2–3 nodes, 1–2 edges per node into the next layer, one objective node `obj` after the last layer; `elite`, `rest`, `crisis` never in the first layer, ≤ 1 `crisis` and none below danger 3; every layer has a combat-kind node. Fog: node types are shown for visited nodes and within `reveal` steps (`1` + 1 for a party defect with `expedition.reveal` (`echo_bleed`) + 1 for a rumor-sourced mission). `unknown` nodes resolve on entry by `resolvesTo` weights.
- **Run.** Cache nodes roll `loot_cache` into the run (banked only on return); rest nodes spend `suppliesPerUnit × able party` carried supplies (or say `No supplies to rest.`); combat nodes store the encounter, the app starts it with `combat/start { expedition: true, bankLoot: false }` and `expedition/resolve_combat` takes the result **once** (`pending.prevCombatId`); event nodes use `dilemmaTemplates` with `scale: 'minor'` (fixed options, each with a cost; options may need a social rank or carried supplies/credits). There are no consumables: `expedition/treat` spends 1 carried supply for +20 % max HP or −10 stress.
- **Return and retreat.** `endExpedition`: carried supplies come home; success banks the loot and completes the mission, otherwise the loot is dropped; breakdowns are released (a named unit gets an `after_breakdown` night entry); queued relation hints are deduplicated and applied through `applyIntents` in batches of `maxEventsPerExchange`; `lastExpedition` (the after-action report) is written; slots are spent; a director request opens. A win with nobody able to go on forces a retreat in the same dispatch.
- **After-action report** always exists as deterministic lines (`reportLines`); the `expedition_recap` narrative (main model, setting `expeditionRecap`) is added on top and stored with `expedition/set_recap` (stale report ids refused, text stripped to plain text, ≤ 1200 characters). The debrief is an optional free scene (`origin: 'debrief'`, location `garage`).
- **Incoming named units:** world effect `incoming_unit` raises `world.incomingUnits`; `squad/add_named { unit }` (profile validated like a re-sync plus the baseline ranges, joins the roster or reserve) or `squad/decline_incoming` (a grunt joins). Both need a free bed.
- **Clearance:** world effect `clearance { tier }` sets `world.clearanceTier = max(current, tier)`, capped at 3 (P4's `levelCap`).
- **Context:** the `world` provider (priority 50, trimmed before P3's promises) adds up to three sentences: the last expedition (within 3 days), one ongoing thread, visible clocks above half.
- **Settings:** `directorEnabled` (default on), `beatCooldownDays` (1–14, default 3), `expeditionRecap` (default on); SYS section World.
- **UI:** MAP tab (image with SVG hotspots from `AppDeps.assetUrl('content/core/map/world.png')`, otherwise an ASCII 3×3 grid), OPS mission board + RUMOR MILL + intake and report banners, the expedition screen (planner, node map, run view, combat/event panels, report). The OPS tab badge counts new command/story offers.
- **Saves:** campaign state stays `version: 1`; every P5 field is optional or empty in older saves; a pre-P5 save is seeded by `world/seed` on load. The app flushes the save at once on every `expedition_*` event.

### Differences from the draft above
- Clocks hold inline world effects in `onFill` (definitions live in the new `clocks` registry); factions are the `corporations` registry (own corporation starts at +10).
- The draft's `rewards` object on a mission is computed on completion from `rewardTiers`; the model never sets amounts.
- Intents of an expedition are applied by the engine on return, not inside the debrief scene.
- `expedition_node` events carry `nodeType` (not `type`); `mapRows` has one extra row for the objective.
- Hint evidence, rest and field-treatment texts are authored in code (`expedition.ts`); everything content-like is JSON.

### Decisions taken while implementing (rulings)

Where the plan or spec was silent, ambiguous or in conflict with the P0–P4 code, these calls were made. Each can be reversed cheaply; the cost is noted where it is not obvious.

**Content (`content/core`)**
- Story missions are `tpl_vesper_beat_N` / `tpl_kestrel_beat_N` (corporation key, not the start id) and carry `factionId` = the start's corporation, so a tier's `faction` has an effect. `bloom_d7` and `corridor_quota` start with 1 filled segment.
- `unit_event`s with `valueAxes` use `decision_aligned` (P3's `validateIntents` keeps axes only on `decision_aligned` / `decision_violated`; axes on `sided_with` were silently dropped). Units whose values match an axis direction gain, the others lose.
- A `win` objective must use a combat-kind node (loader check); `startingRegionId` is now a checked reference (the p1 test fixture got a minimal `regions.json`).

**Engine rules**
- `WorldEffect` is a hand-written TS type in `engine/world/types.ts` (the engine may not import content schemas); keep it in step with `WorldEffectSchema`.
- `loot` effect `rolls` = repeated rolls of the table; repeat clocks reset to 0 **before** `onFill` runs; `party_hp`/`carried_supplies` emit no events (the run log carries them); `leash` emits `leash_changed { amount, left }`.
- Boards: `boardRoom = missionBoardSize − offered.length`; a refused offer returns `{ mission: null }` with no events. The `offer_mission` effect uses the template's first region, else the first known one.
- Rumors: `postRumor` returns the rumor (or `null`); callers emit `rumorPostedEvent(r)`. A rumor whose mission lead is missing or invalid is rejected whole by the director validator.
- The mission-completed hook is registered in `actions/world.ts` (`registerMissionCompletedHook`) because `effects`/`spine`/`missions` import each other and a registration at module load would hit a temporal dead zone.
- `completeBeat` advances `spineProgress` and clears `spine.proposed` **before** running `onComplete` (a flag set there cannot re-complete the beat). `proposeBeat` throws unless the beat is the current, ready, unproposed one; the cooldown is the caller's policy.
- Node map: each node first links to its nearest next-layer index, uncovered nodes are taken by the nearest node with room, then a node may add a second edge (keeps the 1–2 edge invariant); `mapRows` returns one extra row for the objective; a region that cannot draw a combat-kind node for a layer skips that rule silently (only "no node type at all" throws).
- Expedition: `checkExpedition` also requires every party unit to be on `roster.activeIds` (P4's `checkStart` demands it); `expedition_node` events carry `nodeType` (not `type`); random events exclude any template pinned by `objectiveEventId`; `checkDeparture` and `poiCooldownReason` are exported so the UI shows the engine's own reasons; `buildMission` (extracted from `offerMission`) builds POI runs; a win with an empty front row moves the first back-row unit forward.
- Content removed under a save: a node type, event or encounter that can no longer be played resolves as `Nothing here.` and finishes an objective node; a vanished story mission frees its beat.
- Director: `answerRequest` is the one path for `director/apply`, `director/fallback` and the day-end fallback; `director_applied` counts `mission_offered` events (a beat's mission counts) and carries `fallback: true` only for fallback answers. Digest: newest 4 flag ids per thread, story-only templates left out, ≤ 6 dormant threads (to stay under 4000 characters). Fallback side missions are templates that allow `side` but not `command` and are not a POI template (core: `tpl_hunt`); its command cadence counts `offeredDay` over offered + active + completed command missions. The plan's test name "three advances of 2 keep the total at 3" contradicts its own rule ("later ones rejected"): the rule is implemented (`[2,2,2]` on three clocks keeps the first; `[1,1,1,1]` keeps three).
- `answerRequest`/`openRequest` details added after review: the first command-capable offer of a tick becomes the single open command mission, others are `side`; reopening a thread counts against the 6-open limit and old closed/dormant threads are trimmed; a scout request that is open when a full request arrives remembers it (`world.director.after`) and opens it as soon as the scout is answered; the fallback advances a clock once per day (`world.director.lastClockDay`); the campaign mirrors the global `beatCooldownDays` into `settings.beatCooldownDays` (`campaign/set_beat_cooldown`, synced by the app on load and on setting change) so fallback and day-end answers use it; `expedition/retreat` first takes in a decided fight; `lastExpedition.day` is the day the squad came back.
- Dispatch guard during a run also lets `relations/commander_injured` through (a Commander Crisis happens only inside a run).
- Report text: the combat log line names the enemies; recap cleaning strips tags and script/style blocks, collapses whitespace and cuts to 1200; an expedition returned today reads "today" in the context line.

**App and UI**
- `WorldDeps` (`src/world/deps.ts`) is a structural subset of `AliusApp` (`dispatch`, `current`). Controllers never toast `chat_changed`, `combat_open` or `Stale director answer.`; a director answer that comes due during a fight is retried on `combat_ended`; the in-flight key of a request includes the chat id.
- RETREAT confirmation is inline in the run view; an event whose template vanished offers `[ CONTINUE ]`; `renderNodeMap` takes optional `labels`; the OPS tab gained `onOpenReport` (`REPORT READY`) and the badge counts new command/story offers not yet drawn in the tab; the expedition screen keeps the planner draft and debrief picks across refreshes.
- After the report closes, a night knock that was queued by the return is shown (not lost); a fight's CONTINUE returns to the expedition (or to the PDA when the fight ended the run; the report follows); a plan and the OPS "seen" memory are reset on a chat switch.
- `expedition_*` events flush the save at once (reload mid-run resumes at the same node).
- `tests/app.test.ts` lists the new `map` tab and `expedition` screen.

### P6 additions
- `unit_event` outside an expedition applies at once through `applyEventToUnit` to `EffectSource.units` (default: the active roster; `targets: named` only named units), then each unit is re-evaluated. New world effect `thread_flag` (a dynamic flag in a thread's namespace).
- `finishEventNode(draft, nodeId, text, data?)` is exported from `world/expedition.ts` (used by `chooseOption` and by dilemmas); `expedition/choose` is refused while a dilemma for that node is open.
- The two beat-4 events (`evt_vesper_choice`, `evt_kestrel_choice`) are now `defining` templates with a `generate` block: the app turns the pinned objective event into a `dilemma/request` (when `dilemmasEnabled`), the model writes the three options (exactly one allowed flag each) and the authored block is the fallback; the beat-5 flag completion is unchanged. `dilemma/` actions are allowed while an expedition is open; a presented dilemma blocks `expedition/start`.
- `startExpedition` may open a mission-start desertion confrontation instead of starting; `checkExpedition` then says `<name> is about to walk: deal with it first.`
