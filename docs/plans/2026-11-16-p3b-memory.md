# P3b Memory Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The squad remembers what happens to it, and the main model is told, within a budget the player sets:
- engine events (runs, combat, votes, scapegoat, dilemmas, discipline, P9c pressure) become facts with the right audience, and the rest of the squad hears them later as rumors;
- old facts are folded into a per-unit dossier instead of being deleted;
- the relation journal, a short "recently in the unit" chronicle and a recap of recent DMs reach the prompt;
- long scenes are summarized whole, and old scenes can be hidden from the ST chat;
- memory has presets, its own token share, a fill indicator and a MEMORY view (pin and forget; edit with the edit lock off);
- a fact can be hidden from the commander (for P12).

**Architecture:**
- **Engine.** `src/engine/memory.ts` becomes the folder `src/engine/memory/`. Its `index.ts` re-exports everything `memory.ts` exported, so no importer changes. New files: `config.ts`, `resolvers.ts`, `remember.ts`, `rumors.ts`, `audience.ts`, `fold.ts`, `journal.ts`, `scenes.ts`. The engine stays pure. Rumor spread uses a string hash, never the RNG.
- **Hook points.**
  - `dispatch` calls `rememberEvents` after a successful handler (and `carryVote`), before the ledger.
  - Rumors plug into the existing `dm_rumors` day-end hook.
  - `scene/end` writes the chronicle audience and the scene's chat range.
- **New actions** (new file `src/engine/actions/memory.ts`): `memory/configure`, `memory/pin`, `memory/forget`, `memory/edit`, `memory/fold`, `memory/edit_dossier`, `memory/rumor_text`, `memory/hidden`. `scene/digest` goes in `actions/scene.ts`, beside `memory/compact`, which stays where it is.
- **LLM and context.**
  - `ContextBuilder` gets provider groups and a guaranteed `memory` share.
  - The memory providers live in `src/scene/memoryContext.ts`.
  - New call types: `memory_fold` and `rumor_retell`, plus a `digest` mode of `scene_summary`.
  - One controller, `src/scene/memoryController.ts`, runs the fold, the retelling, the digest and the scene hiding, the way `runCompaction` does.
- **ST.** The adapter gets `hideMessages` and `unhideMessages` (the ST commands `/hide` and `/unhide`).
- **UI.** SYS › MEMORY (presets, numbers, the fill indicator), a MEMORY block in each unit's block in the SQUAD tab, and a world MEMORY block in SYS. Glossary entries and an analysis provider.
- **Chunks.** (a) Tasks 1–8, the engine. (b) Tasks 9–12, context and LLM. (c) Tasks 13–16, ST, UI and docs.

**Tech Stack:** TypeScript 5 (strict), esbuild, zod 3, vitest (+ jsdom for UI). No new dependencies.

**Spec:** `docs/packages/P3b-memory.md`. Read these before Task 1:

## Global Constraints

- **English and safe text.** Everything is in English. UI text goes through `h()` / `textContent`, never `innerHTML`.
- **Engine purity.**
  - `src/engine/**` stays pure (`tests/architecture.test.ts`).
  - `src/engine/memory/` imports no UI, `llm` or `st` code.
  - `power/state.ts` and `personal/state.ts` stay leaves: memory imports them for types only.
- **The engine decides.**
  - Which event is remembered, who knows it, when a rumor spreads and what is folded are engine computations.
  - Models only word things (the fold, the retelling, the digest) and never write numbers.
  - P3b adds **no new intent** and does not change the `intent_extract` input.
- **No new RNG draw (spec acceptance 7).**
  - Rumor timing is `hashDay(factId, unitId, window)`, FNV-1a over the string.
  - Every seeded test from before P3b keeps its RNG state.
  - If a change moves a seeded test, **stop and report**.
- **No id shift.** Facts written by a memory rule take their ids from their own counter (`memory.nextRememberId`, prefix `fr`), following P9c's `nextPersonalId`. The campaign counter `memory.nextId` is never advanced by P3b, so every id an existing test asserts (`n3`, `c12`, `f2`, …) stays the same.
- **Privacy per audience.** Nothing private reaches a shared prompt:
  - a fact only if every present unit knows it (as today);
  - a chronicle entry only if its audience includes every present unit;
  - a dossier `own` part only in a private scene or a DM with her;
  - journal evidence only in a private scene;
  - the DM recap only in a private scene.
- **Squad secrets stay P9c's.** Nothing reads `personal.secrets[].text`, and no memory rule turns a kept secret into a `Fact`.
- **Read by field, never by id.** Rules are read by `event` and `when`. Resolvers are keyed by event type (a closed vocabulary, like intent types). No code tests a rule id, a template id or an option id, except the existing `scapegoatOptionId`.
- **Spec numbers.**
  - The preset table (§1).
  - The rule table (§2.1), with texts marked `AUTHOR TO WRITE`.
  - Dossier caps: `own` 500 chars, `shared` 400.
  - Fold batch: 6.
  - Digest: threshold 2500 tokens, keeps the last 4 messages, at most 800 chars.
  - Rumor windows: fast 2 days, slow 4, halved at importance ≥ 4 (minimum 1).
  - Pinned retrieval bonus: +2.
  - Hard ceiling: `factsMax × 1.25`.
  - Default `contextTokenCap`: 1600.
  - Budgets: `memory_fold` 500, `rumor_retell` 200.
- **Ids.**
  - No new directive ids.
  - Glossary: `memory`, `memory_fill`, `memory_preset`, `memory_budget`, `dossier`, `rumor`, `pinned_fact`, `hidden_scenes`.
  - Call types: `memory_fold`, `rumor_retell`.
- **Text.**
  - No pronoun for the commander in any text (lore §0); `tests/content/pronouns.test.ts` covers the new registry and the new prompt files.
  - Every new chip, card, stat and option carries `data-analyze` and has a glossary entry.
- **Old saves.**
  - Every new field is optional, and the state version stays 1.
  - Absent `memory.config` reads as `normal`.
  - A chronicle entry without `audience` is LOG-only.
  - A fact without the new fields reads as unpinned, seen and known to the commander.

## Rulings carried over from the user (2026-11-16)

These are the user's answers to the first draft of this plan. Task 16 copies them into the spec's **Implemented as**.

- **What is remembered.** All four groups: runs and combat; power decisions (votes, scapegoat, leader, countermand, rations); discipline and dilemmas; P9c personal pressure (decor, tokens, bookings, wagers, intercepted messages). Spec §2.1 is the exhaustive v1 list. A site that already writes a fact gets no rule.
- **Who learns.** Witnesses know at once; the rest hear it as a rumor over 1–2 days. Spread is deterministic.
- **Rumor mode.** Both modes, chosen in the settings. `plain` is the default and makes no call. In `model` mode the mechanic retells the rumor once per fact.
- **Forgetting.** The mechanic folds old facts into a per-unit dossier. Folding runs **when memory fills** (`foldDue`), not on a schedule. The number of facts kept is a setting, and the fill is shown.
- **Settings.** Presets plus fields. The fields can be edited only with the edit lock off (`editLock`); there is no new "advanced" switch.
- **Memory UI.** In normal mode: view, pin and forget. With the edit lock off: also edit the fact text, the dossier and the numbers.
- **Journal in the prompt.** Per present unit, the last `journalLines` events of kind `event` with severity ≥ `moderate`, plus any severity from the last 2 days. Evidence appears in a private scene only; a group scene gets types and days only.
- **Chronicle in the prompt.** "Recently in the unit": the last `chronicleDays` days plus the newest 1 week entry (`long`: 2), filtered by audience. It reaches scenes, the block outside a scene (public entries only) and `director_tick`.
- **DMs.** A private scene with her gets a recap of recent DMs. DM fact extraction stays as it is. `dm_reply` also gets her dossier and journal.
- **Hidden from the commander.** Lay it down now: `Fact.hiddenFromCommander`, a Knowledge rule and the prompt wording. v1 core rules create none.
- **Extras.** All four are in v1: whole-scene digest, hiding old scenes (off by default), memory's own budget, memory in calls outside a scene.
- **Order.** P3b comes before P10b (already in §9 and `ROADMAP-next.md`).

## Findings from the code (decisions already made)

These were found by reading the code at `0d4a362`. Where a finding refines the spec, Task 16 records it in **Implemented as**.

1. **Rumors use the existing hook.** `calendar.ts` already has a pluggable `dm_rumors` step, which P3, P9d and P9c use. `spreadRumors` is registered there with `registerDayEndStep('dm_rumors', …)` in `actions/memory.ts`. `DAY_END_STEPS` is not changed, so the `day_end_step` events stay the same. The hook runs on a copy and draws nothing, so its place in the order does not matter.
2. **Events from a day end are seen.** Day-end steps run inside the handler (`consumeSlots`), so `mutiny_started`, `unit_deserted` and others reach `rememberEvents` in the same dispatch. Combat events (`breakdown`, `order_refused`, sent through `ectx.emit`) are returned by `combat/*` handlers.
3. **Resolvers return named id groups.** The spec's single `subjectIds` cannot express "the run fact is the party's, the death fact is about the dead". Each resolver therefore returns `{ ids: Record<string, string[]>, vars: Record<string, string> }` and declares its group and var names in `RESOLVER_SHAPES`:
   - `about` names an id group or `world`;
   - `audience` is an id group, `present`, `squad` or `public`, or a list of groups (their union);
   - `when` matches `vars`, where `true` means the var or group is non-empty and `false` means it is empty.

   The content check validates all three against the shape.
4. **`dilemma_resolved` lacks its context.** `flow.ts` deletes `open` before it emits the event. The emitter gets three optional fields: `context`, `optionId` (the authored option id that `scapegoatOptionId` reads) and `subjectId`. `activity_done` gets an optional `slot` (the slot spent). No existing field is renamed.
5. **The expedition report already keeps hidden injuries out.** `hideInjuries` skips the units in `injuries`/`deaths`, and a hidden-injury unit is never in `report.injuries`. The "came back wounded" fact therefore never names a hidden injury. A test pins this.
6. **Scene ranges cannot live on the chronicle line.** `runCompaction` folds scene lines into a day entry on the next `day_started`, which would lose a range stored there. `scene/end` therefore records the range in `memory.scenes?: Array<{ sceneId; from; to; summarized: boolean }>` (the last 50 ended scenes). The payload gains `endIndex`, which the controller sets to `st.chatLength() − 1`. This replaces the spec's `memory.summarized`.
7. **Hidden messages are system messages.** ST's `/hide` sets `is_system`, and `mapChatMessages` already skips `is_system`. Old hidden scenes therefore vanish from every Alius read, which is fine because only ended scenes are hidden. `/unhide` clears `is_system` on the whole range, which would turn real system messages visible. So `hideMessages(from, to)` hides only the runs of messages that are not system messages and **returns the ranges it hid**; only those ranges are recorded and later unhidden.
8. **DM retrieval.** `comms.ts` calls `retrieveFacts(…, 3)` and `dmReply` caps at `FACTS_USED = 3`. Under P3b the DM asks for `ceil(retrievalK / 2)` facts, and `FACTS_USED` becomes 4 (the `long` preset gives 4).
9. **Journal wording.** No label table for relation events exists in code. `eventDeltas` rows (49, each with `cause`, e.g. "You praised her") gain an optional `journal` phrase written in the third person ("the commander praised her"), marked `AUTHOR TO WRITE`. Without it, the type is used with underscores turned into spaces. The internal types (`INTERNAL_HISTORY_TYPES`, e.g. `stress_high`) are never shown.
10. **The out-of-scene block.** Outside a scene only the header and `world_settings` render today; every scene provider returns `null`. The memory group adds the world dossier `shared` part and the public `recent` lines there.
11. **The digest needs the content exclusion.** `scene_summary` marks flagged lines and lists `excluded` categories (P9d). The `digest` mode takes the same `excluded` and `flagged` input.
12. **A wager void is not remembered.** A `wager_resolved` with `winner: 'void'` makes the resolver return `null`. The stake and game names go through `contentAllowed`; a disabled one reads "a wager".
13. **`contextTokenCap`.** Settings are stored whole, so an existing install keeps its stored 1200; only new installs get 1600. SYS warns when `memoryTokens > contextTokenCap / 2`.

## Review Focus

1. **A private thing in a group scene.** A two-person scene line, an `own` dossier, journal evidence, a DM recap or a fact one present unit lacks must never render when a third unit is present. Pinned by one table test over every memory provider (Task 10, `nothing private renders in a group scene`).
2. **Unhiding something Alius did not hide.** A system message inside a scene range (a narrator line, a deserter notice) must stay system after hiding is turned off. If the chat got shorter since the hide, a recorded range past the end is dropped, not sent. Pinned in Task 13 (`a system message in the range stays system after unhide`, `a range past the chat end is dropped`).
3. **A fold answer that arrives late.** A fact added or pinned between `foldDue` and the answer, or a chat switch, must make the controller drop the answer, never fold the wrong set. Pinned in Task 6 (`a stale fold is refused`) and Task 11 (`a chat switch mid-call drops the answer`).
4. **An old save.** A P9c-era save with 120 facts, chronicle entries without audience and no `memory.config` must load, read `normal`, put no old chronicle line into a prompt and fold nothing until something is due. Pinned in Task 1 (`an old save loads and reads normal`) and Task 7 (`an old entry without audience never reaches recentLines`).
5. **Memory never starves the scene.** When `memoryTokens ≥ contextTokenCap`, the header, the scene header and the units still render; a huge dossier is cut line by line and never dropped whole. Pinned in Task 9 (`share ≥ cap still renders the header and units`, `a large memory provider is cut, not dropped`).
